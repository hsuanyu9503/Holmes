# 606 情報局｜連線模式 v2.5.2（網頁內 Supabase 設定）

沿用 v2.5.1 已修正的骰子與代號機制，新增網頁右上角的 **⚙ 連線設定**，讓教師可以直接在瀏覽器輸入 Supabase 公開連線資訊，無須自行編輯 JavaScript。原有單機版 `index.html`、骰子邏輯、情報卡資料與 SQL 均未修改。

## 本次新增（v2.5.2）

- 在 `online.html` 右上角新增小型「⚙ 連線設定」入口（綠點＝已設定；黃色點＝尚未設定），桌面和手機都可操作。
- 點開設定視窗即可輸入 **Project URL** 與 **Publishable key／legacy anon key**，支援檢視、隱藏金鑰與清除本機設定。只允許 Supabase 專案網址與公開用途金鑰；會拒絕 `sb_secret_...` 與 JWT `service_role`。
- 儲存後自動重新載入連線模式；設定存在當前瀏覽器的 `localStorage`，同一台裝置重新開啟不必重填。切換不同 Supabase 專案時，會清除先前的「上次房間」紀錄以避免誤連，但不會刪除伺服器資料。
- **教室加入便利性：** 主控端的「複製邀請連結」除了房間碼，也會附上 Supabase **公開** URL 與公開金鑰於網址片段（`#` 後）。玩家開啟邀請連結即可自動儲存連線設定；接收後從網址列移除該片段。若已設定的是不同專案，會先詢問是否切換。**直接在空白裝置輸入六碼房間碼，仍須先設定相同 Supabase 專案。**
- 保留 `online-config.js` 作為可選的網站預設設定檔；若網站已配置預設值，依舊可使用，不會強迫重新設定。**瀏覽器已儲存的設定優先於預設檔案。**
- 無新增 SQL；如已部署 v2.5.1，**只要覆蓋網站前端檔案即可，不需重跑 SQL，也不會清除情報卡或遊戲資料**。



## 本版修正重點

- **雙色骰子各司其職：** 藍色骰子選「列」，紅色骰子選「欄」。即使兩顆骰子點數相同，因顏色不同仍是明確的一種組合。
- **3×3 情報卡（9 格）：** 藍色六面骰 1～6，紅色特殊六面骰 1/1/2/2/3/3。對照表為 **6 列 × 3 欄，共 18 個位置**，A1～C3 共 9 個代號，每個剛好出現 **2 次**。
- **4×4 情報卡（16 格）：** 藍色八面骰 1～8，紅色普通六面骰 1～6。對照表為 **8 列 × 6 欄，共 48 個位置**，A1～D4 共 16 個代號，每個剛好出現 **3 次**；**不重擲 5、6**。
- 每個骰子組合只對應碼表的一個位置；同一個代號允許出現 2／3 次，最後都指向情報卡**同一個格子、同一份情報**。對照表在每輪分配角色時重新生成，所有情報員共用同一張。
- 所有人都可以看見**公開骰子點數**；臥底和未揭曉的主控端**不會收到**代號或對照表，避免透過瀏覽器檢視前端資料取得答案。主控端與臥底於答案公布階段才收到真正代號。
- 3×3／4×4 情報卡的資料編輯結構不變，舊情報卡**不需要重建**。

## 部署方式（請依目前 Supabase 專案的狀態二選一）

### A. 第一次部署，使用全新的 Supabase 測試專案

1. Supabase → Authentication → Providers 啟用 **Anonymous Sign-ins**；請視情況設定 CAPTCHA 與防濫用措施。
2. Supabase → SQL Editor 執行 `supabase/606-online-v2.5.1.sql`（**整份一次執行**）。此檔含資料表、受保護 schema、RLS、Realtime、RPC 及明確的 `GRANT`；針對 2026/10/30 的 Data API 權限規則預先設計。
3. 部署完成後，在連線模式 `online.html` 右上角點「⚙ 連線設定」，貼上 Project URL 和 **公開金鑰**（publishable key 或 legacy anon key），點「儲存並重新連線」。**不必編輯 `online-config.js`**。嚴禁輸入 `service_role`、`sb_secret_...`、資料庫密碼。
4. 將整個網站目錄部署至 GitHub Pages（`index.html`、`online.html`、`online-config.js`、`assets/`），接著進行前述設定。請注意：瀏覽器中的設定不是網站的全站預設值；其他裝置可透過主控邀請連結自動取得公開設定。
5. 主控建立、啟用情報卡，並進行多人測試。

### B. 已經部署 v2.5.0 的 Supabase 測試專案

1. **先確認所有遊戲均已結束且房間已回到等待區（lobby），或已關閉。** 升級檔會檢查是否有進行中的房間，若有會報錯並完整回滾，不會中途更換碼表。
2. 在既有 Supabase 專案 SQL Editor 只執行 `supabase/606-online-v2.5.0-to-v2.5.1.sql`。它只更新兩個 RPC 函式，清除等待／關閉房間中不再使用的舊碼表；**保留情報卡、房間及玩家資料**。既有的 `rerolls` 欄位可留存但不再使用。
3. 更新 GitHub Pages 網頁前端檔案（尤其是 `online.html`、`assets/online.js`、`assets/online.css`）；已用 `online-config.js` 配置的專案仍可沿用，不必覆蓋原有設定。此版本也可以改從右上角介面設定。
4. 重新整理頁面或清除快取後，再建立新一輪開始測試。

**切勿在已部署 v2.5.0 的專案執行「全新部署 SQL」：** 它包含已存在的 RLS policy，不是升級用檔案。全新 SQL 與升級 SQL 擇一，不要兩份都執行。

## 遊戲流程

1. 主控建立 3×3 或 4×4 房間，3～8 位玩家由個別裝置加入；每局固定一位臥底。
2. 主控分配身分時，伺服器建立本輪唯一的隨機對照表，僅對情報員透過授權 RPC 回傳；臥底看不到。
3. 玩家私下看角色卡並確認；主控點選抽骰，伺服器分別取得藍、紅兩顆骰子的點數，使用 **(藍骰 - 1) × 對照表欄數 + (紅骰 - 1)** 取出代號；**不能**單純對骰子點數取模後直接拼出 A1、B2 等代號。
4. 所有人看見骰子點數；情報員查看私人對照表的「藍色列 × 紅色欄」，找到機密代號；臥底只能根據稍後的情報卡與口頭線索猜測。
5. 主控抽取情報卡；全員同步顯示，只有情報員能使用代號找到題卡對應詞彙。對照表上的相同代號永遠映射到情報卡上同一格。
6. 現場口頭討論、投票後，主控先揭曉臥底，等臥底猜測後才公布機密代號與正確情報；接著可進入下一輪。

## 隱私與使用限制

- 角色、亂數對照表與骰子對應代號由 Supabase 受保護 schema 和授權 RPC 處理，不以公開 Realtime 資料列傳送機密對照表。
- 連線需要 Supabase 與 Supabase JS CDN。匿名使用者與資料以目前瀏覽器登入身分綁定，清除網站資料或更換裝置可能無法取回原房主身分／情報卡；正式持久化管理可另行加教師登入。
- SQL 尚未在實際 Supabase 專案執行跨裝置整合測試；前端測試使用模擬資料。請先驗收後再用於正式活動。
- 本版本只修正連線模式；單機模式、討論及投票的現場口頭流程維持不變。

## 從 v2.5.1 升級到本版（v2.5.2）

只需更新 `online.html`、`assets/online.css`、`assets/online.js`，以及本次說明文件；`online-config.js` 可沿用原本內容。**不需執行 SQL**，完整部署包內保留兩種原 SQL 僅供新安裝／舊版升級使用。前端版本查詢參數已改為 `v=2.5.2` 以減少快取干擾。

> 安全提醒：Supabase publishable／anon key 是設計給前端使用的公開識別值，能隨邀請連結分享；它**不是**資料庫密碼或管理員金鑰。真正的權限仍必須透過已部署的 RLS、GRANT 和 RPC 控制。若不希望公開專案資訊出現在邀請連結，應在所有裝置各自設定，或由網站管理者在 `online-config.js` 配置共用公開值。
