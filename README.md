# 606 情報局 v2.5.7｜多人加入、管理玩家與登入修復

## 本次修改

1. **修復匿名身分殘留**：開房／加入前會向 Supabase 驗證登入身分。發現帳號被刪除或憑證失效時，先清除該登入憑證再建立新的匿名身分；如進行中的操作遇到 `intel606_rooms_host_id_fkey`，會提示重新建立房間，避免一直重用已刪除的 `host_id`。
2. **每分頁獨立玩家身分**：主控端保留既有 Supabase localStorage 登入（保護原情報卡所有權）；學生端改以 sessionStorage 保存登入，同一瀏覽器多個分頁掃描邀請連結不會誤共用同一位玩家身分。主控與玩家可分別重整恢復；學生關掉該分頁後，仍可能無法恢復匿名身分，建議遊戲期間保留分頁。
3. **房間管理直接列出玩家**：在主控端展開「⚙ 房間管理」後，可於等待玩家階段移除指定座位；保留二次確認。開始遊戲後不可移除玩家，避免本輪的臥底抽籤與準備狀態錯置。移除玩家只操作 `intel606_members`，**不刪除 auth.users**。
4. **4×4 隨機代碼表修復**：將伺服器端均勻亂數函式上限由 32 修正為 256，以支援打亂 48 格的代碼表；16組代號各有3種抽取途徑的規則不變。
5. **QR code 改為本機產生**：不再把邀請連結傳給外部 QR code API。使用內建 QR 繪製模組產生 SVG，學生掃描仍可帶入房間代碼及**公開** Supabase 設定；禁止加入 secret/service_role 金鑰。

## 部署方式

**先暫停所有遊戲。建議先在測試專案備份與驗證，再套用正式專案。**

- 已安裝 v2.5.4、v2.5.5、v2.5.6 任一版本 SQL 的專案：在 Supabase SQL Editor **只執行 `supabase/606-online-v2.5.4-to-v2.5.7.sql`**。此為相容的統一升級 SQL，重複執行也不刪現有情報卡。
- 確定已完整執行 v2.5.5 SQL 的專案：也可以選擇只執行較小的 `supabase/606-online-v2.5.6-to-v2.5.7.sql`，但**二選一**即可。
- **全新資料庫**：只執行 `supabase/606-online-v2.5.7.sql`。
- 仍使用 v2.5.0 SQL：先完成 `supabase/606-online-v2.5.0-to-v2.5.1.sql`，再執行統一升級 SQL。

更新 GitHub Pages 根目錄所有網站檔案，至少需包含：`online.html`、`assets/online-v2.5.7.js`、`assets/online-v2.5.7.css`、`assets/qr-local-v2.5.7.js`。新版採用新檔名避免快取；建議更新整個壓縮包，以免檔案不一致。Supabase 公開設定通常沿用瀏覽器既有資料，無需重填。

## 重要：不要再從 Authentication → Users 刪除玩家來踢人

`public.intel606_rooms.host_id`、`public.intel606_members.user_id` 和 `public.intel606_cards.owner_id` 會參照 `auth.users`。原資料表採 `ON DELETE CASCADE`：**刪除主控匿名帳號會連帶刪除該房間，以及這個帳號所建立的情報卡**。這類既有刪除無法靠新版 SQL 自動還原。

要移除玩家，請在網站主控端的「房間管理」操作。若已刪除主控帳號，請重新整理連線模式，建立新的測試房間。

## 建議驗收

1. 一個主控加三個不同手機或三個以邀請連結開啟的獨立瀏覽器分頁，確認得到 1、2、3 不同座位；主控顯示 3/8。
2. 房間管理移除 2 號後，名單變成兩人，被移除者重新同步會顯示已離開。
3. 3×3 和 4×4 分別開始一次，確認 4×4 不再出現 `invalid random range`。
4. 測試先前已被刪除的匿名登入：新的房間可正常建立；舊的房間不應被誤當成可恢復資料。
5. 掃描 QR code，確認網址指向你的 GitHub Pages，且含正確房間代碼；QR code 在本機產生，不會呼叫第三方 QR 伺服器。

## 測試限制

本次通過 JavaScript 語法與本地 Chromium 模擬 Supabase API 的多人加入、主控移除、失效帳號重建，以及 QR code 解碼測試。尚未連上你的實際 Supabase 專案，SQL、RLS 與跨裝置 Realtime 仍須在你的測試專案驗收。
